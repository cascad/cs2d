# План: графика «Lords of Pain» (Diablo-style) для клиента

> Документ-набросок. **Ничего не внедряем**, только фиксируем «что куда».
> Цель: заменить текущие цветные квадраты на пререндеренные спрайты в стиле Diablo II
> и добавить анимации: бег, удар мечом, dash, блок, получение урона + окружение.

---

## 0. TL;DR — главное, что нужно понять заранее

Сейчас игрок — это **один цветной квадрат**, который мы **вращаем** через
`Quat::from_rotation_z(rotation)` (см. `client/src/systems/interpolate_with_snapshot.rs`).

Пак Lords of Pain — это **пререндеренные 2D-спрайты с 16 направлениями** (как Diablo / Halls of Torment).
Это значит:

- **Спрайт НЕ вращается.** Вместо поворота мы выбираем одну из 16 заранее
  отрисованных «сторон» (N, NNE, NE, … ) по углу `rotation`.
- Каждая анимация (бег, атака…) — это **последовательность кадров (frames)**
  для каждого из 16 направлений.
- Рендер = «выбрать направление» × «выбрать анимацию» × «проигрывать кадры по таймеру».

То есть `rotation` из снапшота превращается не в угол спрайта, а в **индекс направления 0..15**.

## 1. Что это за пак и что из него реально брать

Источник: <https://trevor-pupkin.itch.io/lords-of-pain>

- **DEMO-версия бесплатна** (7.1 MB) — на ней можно собрать весь пайплайн рендера и анимаций.
  Полная версия (£2.99, 109 MB): ~7 персонажей, ~41 проп, ~40 анимаций, 5302 файла.
- Лицензия: можно в free и коммерческих проектах, можно модифицировать,
  **нельзя перепродавать/перераспространять** сами ассеты (даже изменённые).
- Технические особенности (важно для кода):
  - спрайты маленькие (персонаж ~24×40 px внутри кадра), кадр ~256×256;
  - **16 углов (directions)** на каждую анимацию;
  - idle — это **один статичный кадр** (не анимация);
  - файлы лежат покадрово в папках, пример структуры из описания:
    ```
    skeleton_default_attack/
      N/
        skeleton_default_attack_N_900_0.png
        skeleton_default_attack_N_900_1.png
        ...
        skeleton_default_attack_N_900_7.png   ← 8 кадров на направление
      NE/
        ...
    ```
  - итого имя кадра = `<entity>_<anim>_<DIR>_<seq>_<frame>.png`.

### Что нам нужно из пака под твои механики

| Твоя механика      | Что ищем в паке                                  | Если в DEMO нет                                  |
|--------------------|--------------------------------------------------|--------------------------------------------------|
| Бег (run)          | `*_run` / `*_walk` (16 dir, N кадров)            | есть в базовых персонажах                        |
| Idle               | `*_idle` (1 кадр на dir)                          | есть                                             |
| Удар мечом         | `*_attack` (16 dir)                               | есть у player/skeleton                           |
| Получение урона    | `*_hit` / `*_hurt` / `*_damage`                   | если нет — мигание/вспышка цветом (см. §7)       |
| Смерть (для трупа) | `*_death`                                         | у тебя уже есть «труп» — заменить спрайтом        |
| Dash / подкат      | **скорее всего отдельной анимации НЕТ**           | используем `run` + быстрый рывок + эффект (см §6) |
| Блок (щит/меч)     | `*_block` / `*_defend`                            | если нет — поза idle + щит-проп/тинт              |
| Окружение          | props: колонны, кирпич, кости, камни, гемы, пол   | tile пола 256×256 + props свободным размещением   |

> **Реалистично:** dash и block почти наверняка придётся «собирать» из имеющихся
> поз + кода (скорость/таймер/эффект), а не брать готовой анимацией. Это нормально.

## 2. Куда класть ассеты в репозитории

Bevy грузит из `client/assets/`. Предлагаемая раскладка:

```
client/assets/
  sprites/
    player/
      idle/      <DIR>/*.png   (или собранные атласы — см. §4)
      run/       <DIR>/*.png
      attack/    <DIR>/*.png
      block/     <DIR>/*.png
      hit/       <DIR>/*.png
      death/     <DIR>/*.png
    skeleton/
      ...
  env/
    floor/*.png        (тайлы пола 256×256)
    props/*.png        (колонны, кости, камни, гемы…)
  fonts/                ← уже есть (FiraSans-Bold.ttf)
```

> Каталог `assets` сейчас, судя по `startup.rs`, уже используется (грузится `fonts/...`),
> значит путь `client/assets/` рабочий.

## 3. Архитектурное решение: направления вместо поворота

### 3.1 Маппинг угла → направление

`rotation` (радианы, угол на курсор) → индекс направления `0..N-1`:

```rust
// N_DIRS = 16 (или 8, если у демо 8 направлений)
fn dir_index(rotation: f32, n_dirs: usize) -> usize {
    let two_pi = std::f32::consts::TAU;
    let step = two_pi / n_dirs as f32;
    // нормализуем в [0, 2π), сдвигаем на пол-шага для корректного округления
    let a = (rotation.rem_euclid(two_pi) + step * 0.5).rem_euclid(two_pi);
    (a / step) as usize % n_dirs
}
```

Порядок направлений (N, NNE, NE, …) в паке надо сверить с именами папок и завести
таблицу `DIR_NAMES: [&str; 16]`, чтобы индекс совпадал с углом игры
(учитывая, что в Bevy +Y вверх, а 0 рад обычно «вправо/восток»).

### 3.2 Спрайт больше не вращаем

В `interpolate_with_snapshot.rs` строка
```rust
t.rotation = Quat::from_rotation_z(lerp_angle(p0.rotation, p1.rotation, alpha));
```
**заменяется** на: оставить `t.rotation = Quat::IDENTITY`, а `rotation` сложить в
компонент `Facing(f32)`, который потом читает система анимации и выбирает направление.

## 4. Как Bevy 0.16 будет это рисовать

Два пути загрузки кадров. Рекомендация — начать с (A), позже перейти на (B).

### Вариант A (просто): отдельные PNG, меняем `Sprite.image`
- Каждый кадр — отдельный `Handle<Image>`.
- Анимация = по таймеру переключаем `sprite.image = frames[i]`.
- Плюс: минимум кода, легко начать.
- Минус: тысячи хэндлов, больше draw-state-свапов (для прототипа ок).

### Вариант B (правильно): texture atlas
- Кадры одной анимации+направления упаковываются в атлас (`TextureAtlasLayout`),
  переключаем `sprite.texture_atlas.index`.
- Упаковку можно сделать:
  - заранее (TexturePacker / скрипт → один png-лист на анимацию), **или**
  - в рантайме через `TextureAtlasBuilder` на старте загрузки.

Скелет компонента-анимации (псевдо-API Bevy 0.16):

```rust
#[derive(Component)]
struct SpriteAnim {
    clip: AnimClip,        // какой клип сейчас играет
    timer: Timer,          // частота кадров
    frame: usize,          // текущий кадр
    facing: usize,         // индекс направления 0..15
}

// Для варианта B: Sprite::from_atlas_image(image, TextureAtlas { layout, index });
// каждый tick: anim.timer.tick(dt); если finished → frame = (frame+1)%len;
//              sprite.texture_atlas.index = base_index(clip, facing) + frame;
```

### Глубина / порядок отрисовки (важно для diablo-вида)
В top-down/iso объекты ниже по экрану должны перекрывать те, что выше.
Делаем **depth sort по Y**: `transform.translation.z = -y * SOME_SCALE`
(чем меньше Y, тем больше Z → рисуется поверх). Отдельная мелкая система в `PostUpdate`.

## 5. Конечный автомат анимаций (animation state machine)

Состояния и приоритеты (от высокого к низкому):

```
Death  >  Hit  >  Attack  >  Block  >  Dash  >  Run  >  Idle
```

Логика выбора клипа каждый кадр:
1. если мёртв → `Death` (one-shot, потом труп);
2. если активен таймер `hit` → `Hit`;
3. если активен `attack` → `Attack` (one-shot, блокирует смену до конца);
4. если зажат блок → `Block`;
5. если активен `dash` → `Dash`/`Run` ускоренный;
6. если есть движение (скорость > 0) → `Run`;
7. иначе → `Idle`.

`Attack/Hit/Death/Dash` — **one-shot** (играются до конца), `Run/Idle/Block` — **looping**.

## 6. Конкретно по твоим механикам

### Бег (run)
- Берём `run`-клип. Направление — из `Facing`. Скорость кадров фиксированная.
- Триггер: длина вектора движения > 0 (для локального — по инпуту, для remote — по
  разнице позиций между снапшотами).

### Удар мечом (attack)
- One-shot клип `attack`. Запускается по ЛКМ из `send_input` на `did_attack`
  (удар — часть детерминированного тика способностей `tick_abilities`, как рывок;
  отдельного системного `melee_attack` больше нет).
- Урон считает сервер в «середине взмаха» (`MELEE_HIT_DELAY`, `PendingMelee` →
  `resolve_melees`); клиент предсказывает анимацию+декаль локально, а КД
  реконсилирует из снапшота (`melee_cd_left`). Детали — см. `REFACTOR_LOG.md` §5.5.

### Dash / подкат (быстрый рывок)
- **Скорее всего отдельной анимации нет** → реализуем как:
  - кратковременный буст скорости + кулдаун (новый компонент `Dash { timer, cooldown }`);
  - визуально: проигрываем `run` ускоренно, опционально лёгкий «motion blur»/тинт/трейл.
- Это и геймплейная (скорость), и сетевая (надо синхронизировать) механика.

### Блок (щит/меч)
- Если в паке есть `block`/`defend` — looping/hold-клип, пока зажата кнопка.
- Если нет — поза idle нужного направления + флаг `Blocking` (для урон-логики на сервере)
  + визуальный маркер (щит-проп или тинт).

### Получение урона (damage / hit)
- У тебя уже приходит `S2C::PlayerDamaged { id, new_hp, damage }` и есть
  `PlayerDamagedEvent` + всплывашки урона (`spawn_damage_popups`).
- Добавляем реакцию: по этому событию запускаем one-shot `hit`-клип
  (или, если клипа нет — кратковременная красная вспышка `sprite.color`).

## 7. Какие компоненты/ресурсы/системы добавить (карта изменений)

### Новые компоненты (`client/src/components.rs`)
- `Facing(f32)` — текущий угол (вместо вращения transform).
- `SpriteAnim { clip, timer, frame, facing }` — состояние анимации.
- `AnimController { state, attack_timer, hit_timer, blocking, .. }` — машина состояний.
- `Dash { timer, cooldown }` — для рывка.

### Новый ресурс (например `client/src/resources/anim.rs`)
- `AnimAssets` — каталог загруженных клипов:
  `HashMap<(CharKind, Clip), DirectionalClip>`, где `DirectionalClip` хранит
  по направлению либо `Vec<Handle<Image>>` (вариант A), либо `(Handle<TextureAtlasLayout>, base_index, len)` (вариант B).
- Грузится один раз на старте (расширить `load_ui_font`/`setup` или сделать загрузочный стейт).

### Новые системы (`client/src/systems/`)
- `anim_load.rs` — загрузка/сборка клипов в `AnimAssets` (Startup или AppState::Loading).
- `anim_drive.rs` — каждый кадр: тикаем таймер, обновляем `Sprite` (image/atlas index).
- `anim_state.rs` — машина состояний (§5): решает, какой клип играть.
- `facing.rs` — пишет `Facing` из `rotation` (заменяет поворот в interpolate).
- `depth_sort.rs` — `z = f(y)` в `PostUpdate`.
- `dash.rs` — логика рывка (скорость/кулдаун).
- `env_setup.rs` — расстановка пола и пропов (вместо/поверх серых квадратов стен).

### Правки в существующих файлах
- `network.rs::spawn_player` — вместо цветного `Sprite { custom_size, color }` спавнить
  спрайт-героя: `Sprite::from_image(...)` + `SpriteAnim` + `Facing` + `AnimController`.
- `interpolate_with_snapshot.rs` — убрать `Quat::from_rotation_z`, писать `Facing`;
  можно тут же определять «движется/нет» по разнице позиций для remote-игроков.
- `corpse_lc.rs` / death-обработка в `network.rs` — труп = спрайт `death`-клипа,
  а не красный квадрат.
- `main.rs` — зарегистрировать новые системы в нужных стадиях
  (load → Startup/OnEnter; drive/state/facing/dash → Update; depth_sort → PostUpdate).

## 8. Сетевая часть (что синхронизировать)

Сейчас в снапшоте есть: `id, x, y, rotation, stance, hp` (`protocol/src/messages.rs`).
Анимация в основном **выводимая** (derive) на клиенте, но часть состояний надо передавать,
иначе у других игроков не будет видно атаки/блока/дэша.

Варианты:
- **Минимально-инвазивно:** ввести в протокол поле `action: PlayerAction`
  (`None | Attack | Block | Dash | Hit`) в `PlayerSnapshot`, сервер его выставляет.
- Либо отдельные события (как уже сделано для `ShootFx`, `PlayerDamaged`):
  `MeleeAttack { id, dir }`, `Dash { id, dir }` — клиент по ним запускает one-shot клипы.
- `hit`-реакция уже покрыта `PlayerDamaged` (доп. поля не нужны).
- Серверная боёвка (урон мечом, неуязвимость в дэше, снижение урона в блоке) —
  отдельная задача на стороне `server/`, не обязательна для первого визуального этапа.

> Для **чисто визуального прототипа** можно начать вообще без правок протокола:
> анимации локального игрока гонять по инпуту, remote — по движению (run/idle).
> Атаку/дэш/блок других игроков добавить во вторую очередь через события.

## 9. Окружение в стиле Diablo

Из комментариев автора пака: рекомендуется **2D, без тайлмапа**, свободное размещение.

- **Пол:** тайлы 256×256 раскладываем сеткой (можно тайлмапом или просто спрайтами),
  z = самый дальний фон.
- **Стены/props:** колонны, кирпич, кости, камни, гемы — спавним как спрайты
  с участием в depth-sort по Y (чтобы герой заходил за колонну).
- Текущая карта `level_fixed.rs` (`'#'`/`'.'`/`'S'`) остаётся **источником коллизий**
  (`SolidTiles`/`WallAabbCache`), но **визуал** стены меняем: вместо серого квадрата
  рисуем prop/стену из пака. Т.е. логика коллизий не меняется, меняется только спрайт.
- Масштаб: персонаж ~24–40 px, тайл 256 px — надо подобрать общий `scale`
  (например, рисовать тайл в `custom_size` 64–96 px, чтобы герой смотрелся пропорционально).

## 10. Порядок внедрения (поэтапно)

1. **Подготовка ассетов**: скачать DEMO, разложить в `client/assets/sprites/...`,
   свериться с именами папок направлений и числом кадров.
2. **Загрузчик** `AnimAssets` (вариант A — отдельные png).
3. **Спрайт вместо квадрата**: `spawn_player` рисует idle-кадр нужного направления.
4. **Facing**: убрать вращение, выбирать направление по `rotation`.
5. **Run/Idle**: машина состояний + проигрывание кадров.
6. **Depth sort по Y**.
7. **Attack (локально) + Hit (по `PlayerDamaged`)**.
8. **Dash** (скорость+кулдаун+эффект), **Block** (поза/флаг).
9. **Окружение**: пол + props, замена визуала стен.
10. **Сеть**: пробросить action в снапшот/события → атаки/дэш видны у всех.
11. (Опц.) Перевести загрузку на texture atlas (вариант B) для производительности.

## 11. Риски / на что заранее заложиться

- **Количество направлений** в DEMO может быть 8, а не 16 — код `dir_index` параметризуем `n_dirs`.
- **Нет анимаций dash/block** — закладываем «сборку из поз + кода» с самого начала.
- **Порядок/имена направлений** пака ≠ матнаправление углов Bevy — нужна таблица соответствия + флаги flip.
- **Масштаб/пропорции** героя и тайлов — подбирается вручную.
- **Память/хэндлы** при варианте A на полном паке (5302 файла) — грузить только нужных
  персонажей/клипы, не всё подряд; позже атласы.
- Это **не настоящая изометрия** (ромбическая сетка), а top-down с пререндером —
  depth-sort по Y достаточно, проекцию карты менять не нужно.
